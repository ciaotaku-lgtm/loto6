## 2026-08-06

### やったこと

**コードレビューで見つけた3点の指摘と対応**

1. **盤面の列オーバーフロー**（実害あり）— 列が最大13段まで積み上がる瞬間があり、
   `.main-board`の高さ(440px≒10段分)を超えてボールが枠の外にはみ出していた
   （全2125回中311回・約15%で発生）。→ 段数を10→11に拡張し、11段を超えた分は
   最終行にまとめて少しずらして重ね表示するように修正。
2. **`make_loto.py`の出力パスが相対パス** — `CACHE_FILE`は絶対パスなのに
   `loto_analysis.html`の書き出しだけ相対パスだった。別ディレクトリから実行すると
   意図しない場所に生成される事故になりうる。→ `OUTPUT_FILE`として絶対パス化。
3. **CSVパース失敗行が無言でスキップされる** — 将来データ提供元のCSV形式が
   変わったときに、回が欠けても気づけない。→ スキップ件数を警告表示するように。

**盤面の配色は何度か作り直した（経緯を残しておく）**

1. 最初は「1段目=赤、そこから単色でだんだん暗くなる」12段グラデーションを提案・実装。
   OKLCHで検証もパスしたが、本人の感想は「綺麗になったけど楽しさが減った」。
2. 七色(虹)を色相環1方向に回して復活 → 「似た色（青と藍など）が見分けにくい」との指摘。
3. 4バンドに集約(激熱/熱い/ぬるい/冷たい) → 「1段目と2段目が同じ色になるのは
   意味がない、上位ほど区別が必要」との指摘。ここで実データを確認：
   **数字の再登場は上位の段ほど多い**(1段目14.0%, 2段目11.9%, 3段目10.7%…と
   右肩下がり、全2125回・のべ12,707回の再登場を集計)。
4. この実データを基に色案を3つ作り、Artifactで比較ページを提示 →
   **「B案（上位重視案）」を採用**：1〜4段目は単独色、5-6/7-9/10-11+をまとめる7色構成。
   色が近い組み合わせ(赤↔緑、藍↔紫など)は、白/黒/金の縁取りでも判別できるようにした
   (紛らわしいペアが同じ縁取り色にならないよう配置)。
5. 「1段目=直近に出た数字」を示す白縁+金グロー(`.ball.active`)は既存のまま最優先表示。

比較に使ったArtifact: https://claude.ai/code/artifact/be7db7ec-2b42-4faa-bbb4-89b44032a9db
（段の色分け案 比較 — 3案の実データ根拠と配色を並べたページ）

**その他のUI変更**

- 「前へ ◀」ボタンを追加（「次へ ▶」の逆再生。自動再生ボタンを挟んで左右対称に配置）
- 試した末に不採用だったもの: 各ボールに段の文字(A〜L)バッジを表示する案。
  位置(何段目にあるか)で既に段はわかるため、バッジは情報として重複していて

  安易に「補強」しようとすると、既存の手掛かり(位置)と重複するだけになりがち。

### やったこと

**予想タブのボタンが「選べない」不具合の修正**

本人から「カスタム条件のプリセット選択ができない」との指摘。調べると**タップ自体は効いていて
内部状態も変わっていた**が、`.active-toggle`のCSSが`.freq-toggle .btn.active-toggle`と
親を限定した定義だったため、予想タブのプリセットボタンにもカスタム条件ボタンにも当たらず、
**選択しても見た目がまったく変わらなかった**のが原因。セレクタに`.qp-preset-bar`と
`.qp-cond-opts`を追加して解決。
教訓: 新しいUIブロックを追加するとき、既存の状態表現クラス（active-toggle等）を
使い回すなら、そのCSSが親セレクタで限定されていないか確認する。

**予想タブに数字の選択機能を追加**

UIは3案（A:横スクロール1列 / B:6列グリッド / C:モード切替グリッド）を提示して
**A案を採用**（ペアタブの番号ピッカーと見た目が揃う）。指定できる種類は「含める＋除外」の両方。

- タップごとに 指定なし → ◎必ず入れる → ✕除外 → 指定なし と巡回（`qpNumState`）。
- ◎は6個まで、✕は残りが6個を下回らない範囲まで。超えたら理由を表示して弾く。
- 6個すべて◎の場合はその目で固定し、他の条件は判定しない。
- 番号指定は条件より優先。両立しないときは既存の緩和ロジックで**条件の方**を外して警告に出す。
- 生成されたボールのうち◎指定した番号は白い二重枠で表示。
- 検証: ヘッドレスChromeで実際にタップ操作をして300口生成し、◎が必ず入る/✕が一度も出ない/
  同時にガチガチ条件も満たす/7個目の◎が弾かれる、を確認。

**カスタム条件ボタンの見た目を改善（B案）**

**トリビアの「古くなる」対策**

本人から「トリビアの情報が古くなるので気をつけて」との指摘。調べた結果、数値自体は
毎回の生成時に再計算されるので古くならないが、**危ういのは2点**だった。

1. 「どちらも俗説は成立しませんでした」のような**結論の文が固定文**で、数値が動いても
   書き換わらない。→ `myth_verdict()`を追加し、基準値との差が15%未満なら「ほぼ同じ」、
   外れたら「基準値より高め（差+X.XXポイント）」と**データから文章を選ぶ**方式に変更。
   今回追加したカードもすべて同じ方針（固定値・固定結論を書かない）。
2. 集計対象がいつまでのデータか画面上に書かれていない。→ タブ先頭に
   「第1回（2000/10/05）〜第2134回（2026/09/03）の全2134回を集計。データ更新のたびに
   計算し直しています」を常時表示。

**俗説カードをアプリの段に沿った内容に作り直し（重要）**

段の比較がそのまま俗説の検証になる。作り直すにあたり、段ごとの在籍数を実際に数えて確認した:

- 6個ずついるなら公平な抽選での理論値は6÷43＝13.95%。実測はA段13.93%・B段13.81%・
  C段14.47%・D段13.82%で、**ズレは最大0.53ポイント**。
- E段5.70個・F段5.06個と在籍数自体が減っていくことが判明。これが1枚目のカードで
  「move-to-front方式の構造上の性質」と曖昧に書いていた**「崖」の正体**で、
  今回そこまで正確に説明できるようになった。2枚のカードが

**盤面の「縦位置」と「色」は別の指標だと判明（重要）**

ガイドに「上ほど最近＝赤」と書く前に実データで検証したところ、**そうではなかった**。

- 縦位置（段）= その列で自分より上にいる個数（＝自分より後にその列へ入って、まだ抜けていない数）
- 色 = `freshness = currentIndex - lastDrawnAt[num]`（何回前の抽選で出たか）

全2134回を再現して一致率を測ると **A段100% / B段86.1% / C段63.8% / D段40.2% / E段22.1%**、
F段以下は11%以下。色バンドと表示行バンドの全体一致率は **52.2%**。
同じ列の上のボールが再当選して抜けると下は詰まるが色は変わらないため。
バグではなく2つの情報を同時に出している状態なので、ガイドには注意ボックスとして
「位置と色は別々の情報」と明記した。

**段の配色定数をPython側へ集約**

ガイドの色凡例だけが古い色のまま残る事故を防ぐため、JSにベタ書きだった
`TIER_ROWS` / `TIER_LABELS` / `BAND_COLORS` / `BAND_TEXT` / `BAND_RING_COLOR` /
`TIER_TO_BAND` / `NEVER_DRAWN_*` を`make_loto.py`冒頭のPython定数に移し、
アプリのJSテンプレートと`band_legend_rows()`（ガイドの凡例生成）の両方へ流し込む形にした。
**値は1つも変えていない**ことを、変更前後のHTMLを生成して差分ゼロ（コメントとクォート種別のみ）
で確認済み。

なおガイドの凡例は「A段/B段」ではなく**「この回で出たばかり／1回前に出た／…／9回前より古い」**と
色の実際の意味（freshness）で書いている。段名は座標タブの「位置」の話なので混ぜない。

**ガイドは意図的にデータ由来の数値を書いていない**
